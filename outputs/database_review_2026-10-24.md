## Что нужно изменить или реализовать

### 1. Сохранение полного результата HR Intelligence — до интеграции

`message_analysis` содержит только message_id, model_version, topic, sentiment, problem_level, confidence, analyzed_at. В текущем [Analysis](../app/hr/schemas.py) также есть summary, signals с категориями и цитатами, priority и requires_hr. Для ошибок предусмотрены status и error в HRResult.

Нужны хранение этих данных и явная модель попыток анализа. Возможный вариант: расширить таблицу успешного анализа, вынести сигналы в дочернюю таблицу и добавить задания анализа со статусом, попытками и ошибкой. Числовую confidence текущий HR-модуль не возвращает: её следует оставлять NULL, а не придумывать.

Само отсутствие результата уже может служить признаком необработанной работы для простого MVP — это описано в архиве. Но тогда нужно отдельно определить повторные попытки, обработку постоянно ошибочных сообщений и момент завершения эскалации.

Источник: schema.sql:292; docs/transactions.md:174; app/hr/schemas.py:71.

### 2. Категория и приоритет обращения — до интеграции

В `hr_cases` есть общая reason (`explicit_human`, `no_answer`, `problem`, `manual`), но нет категории и приоритета из TicketDraft. Без расширения нельзя полноценно сохранить, например, `access_problem` с приоритетом `medium` или `harassment` с приоритетом `high`.

Добавить категорию, приоритет и связь с результатом анализа. Статус нашего черновика `new` можно явно переводить в `awaiting_hr`.

Сохранение результата анализа, создание нужного обращения и завершение задания следует выполнять одной транзакцией либо через надёжно сохранённое последующее задание. Иначе сбой после сохранения анализа и до открытия обращения может оставить сигнал без эскалации.

Источник: schema.sql:213; operations.sql:409; app/hr/schemas.py:78.

### 3. Router и уточнения — отдельная реализация приложения

В `examples/backend.py` есть каркас обработки inbox, но функция `route(employee, payload)` передаётся снаружи. Правила выбора маршрута и работающие интерфейсы бота ещё не реализованы этим комплектом.

БД допускает несколько одновременно ожидающих событий одного сотрудника. Индекс `employee_plans_one_active` ограничивает количество активных планов, а не вопросов. Дополнительный SQL-прогон подтвердил одновременное ожидание ответа на `task` и `day14`.

Нужно либо последовательно показывать вопросы, либо обязательно связывать ответы с конкретным plan_event. Для неоднозначных сообщений требуется сохранять ожидающее уточнение и исходное сообщение — например, в небольшой таблице pending_interactions. Подменять это состояние полем rag_status не следует.

Источник: schema.sql:119; operations.sql:335; examples/backend.py:110,143.

### 4. Закрытие обращения зависит от подтверждения доставки

Триггер разрешает переход `sent → delivered → closed`. Прямое `sent → closed` отклоняется. Это подтверждено дополнительным тестом: `Invalid transition in hr_cases: sent -> closed`.

Если канал не предоставляет проверяемые delivery receipts, обращение останется в sent. Для запуска нужно определить отдельное бизнес-правило закрытия после принятия отправки либо отделить жизненный цикл обращения от статуса доставки. Сам факт реальной доставки при этом должен сохранять собственный смысл.

Это ограничение также явно описано автором архива в docs/transactions.md:141.

Источник: operations.sql:17; schema.sql:213.

### 5. Авторизация HR остаётся ответственностью backend

Роль `korsik_app` имеет SELECT на прикладные таблицы; построчного разграничения через RLS схема не включает. Объектные права роли проверены, но они сами по себе не изолируют одного HR от сотрудников другого HR.

Все API-запросы должны фильтровать данные по HR из аутентифицированной сессии. В примере есть соответствующая проверка hr_employee(); её необходимо распространить на переписку, обращения, выгрузки и документы и проверить с двумя HR.

Источник: grants.sql:4; examples/backend.py:234.

## Адаптер к текущему HRInput

| Поле HRInput | Источник в БД/событии |
|---|---|
| event_id | Текстовый provider event ID из max_inbox |
| employee_id | Строковое представление внутреннего employees.id с согласованным маппингом |
| source | Результат маршрутизации: message, survey или hr_request |
| survey_id | Для предложенной интеграции — идентификатор персонального employee_plan |
| question_id | Идентификатор конкретного plan_event |
| question | Текст соответствующего plan_event.body |
| score | plan_events.rating для оценки удовлетворённости 1–10 |
| text | Текст сообщения/комментария сотрудника |

Идентификаторы маршрутизации и оценку следует брать из проверенного контекста. Регистрационные поля и подтверждения обычных заданий не следует автоматически направлять как свободные HR-сообщения. Порог комментария в БД зафиксирован как 8; изменение EscalationPolicy требует согласования правил между компонентами.
