# Сверка с korsik_postgresql17.zip

## Результат

Сверены schema.sql, operations.sql, import_format.md, examples/backend.py и
пояснения README из предоставленного архива. Общая БД — схема `korsik`, PostgreSQL 17+.
Она покрывает базовые события info/task/rating/feedback и общую очередь доставки.
Полный ранее разобранный Excel из 26 событий она пока не выражает. Это нельзя
исправить только переименованием ORM-полей или превращением всех вопросов в rating.

Никакие изменения общей БД не применялись. Предложения ниже требуют согласования.
Для совместимой части используется shared_db.py и scheduler.py. Старые таблицы, legacy-код, миграции и демозапуски удалены из основного набора.
Доступный через PATH локальный PostgreSQL — 14.20. Архив требует 17+, поэтому адаптер
проверен по SQL-контракту и синтаксису Python, но не запускался против PostgreSQL 17.
Проверку версии архива не обходили, чужую схему на 14 не запускали.

## Соответствие таблиц и полей

| Step.text / due_at | body / scheduled_at | Соответствуют; даты рассчитывает event_time при assign_plan |
| kind=message | kind=info | Базовое соответствие без изменения БД |
| status=pending | status=scheduled | Базовое соответствие; queued и accepted нельзя смешивать |

| onboarding_messages | messages + outbox | Текст/автор/ключ отдельно от состояния отправки |

Позиции прежнего модуля начинаются с 0, общей схемы — с 1. При будущем переносе
шаблонов применять явное +1. Существующие IDs и историю не переносили автоматически.

## Что сделано на нашей стороне

1. shared_db.py содержит единственный SQL-адаптер общей korsik-схемы.
2. scheduler.py выполняет подготовку и отправку через этот адаптер, без второй очереди.
3. tasks.py регистрирует только общую реализацию; legacy-режим удалён.
4. survey.py проверяет новые типы и возвращает invalid_answer без технического retry.
5. scenario.py и calendar.py читают подготовленный каталог и рассчитывают проект дат;
   в общую БД неподдерживаемые данные не записываются.
6. Старые ORM-модели, миграции автономной БД, Excel-импортёр и демофайлы удалены.
   Никаких CREATE TABLE или изменений общей БД при этом не выполняется.

## Обязательное согласование БД для полного Excel

### 1. Вопросы разных типов и несколько ответов на событие

Проблема: kind допускает только info/task/rating/feedback, а ответ хранится в одной
паре rating/comment. В Excel есть да/нет, один/несколько вариантов, свободный текст,
фото; опрос через две недели содержит 9 вопросов, итоговый — 12.

Предлагаемый минимальный контракт:
- `template_events.definition JSONB NOT NULL DEFAULT '{}'`: ограниченное описание
  вопросов, вариантов и правил; НЕ произвольный workflow или кадровая карточка.
- `plan_events.definition JSONB NOT NULL DEFAULT '{}'`: неизменяемый снимок выбранного
  варианта при назначении; `current_question_code TEXT NULL` — текущий вопрос.
- Допустить kind='survey' в обеих таблицах и связанных CHECK/функциях.
- Одна новая таблица `event_answers`: PK(event_id,question_code), FK event_id→plan_events.id;
  answer_type, rating SMALLINT, value JSONB ограниченного типа, comment TEXT,
  answered_at, commented_at. CHECK рейтинга 1–10 и соответствия типа значения.
- Операция `answer_survey_question(employee_id,event_id,question_code,type,value)`
  проверяет владельца и описание вопроса, сохраняет ответ, применяет условный
  комментарий и продвигает диалог. Общий max_inbox остаётся защитой от повторов.
- Запретить старт второй независимой интерактивной формы одному сотруднику,
  пока первая активна; info-сообщения должны продолжаться. Истечение срока освобождает диалог.

Старые rating/task/feedback продолжат использовать answer_event. Не хранить
единственную копию ответов в max_inbox.payload: это транспортный журнал с отдельным
сроком хранения, он не заменяет бизнес-ответы и аналитику по вопросам.

### 2. Площадка и тип сотрудника

Проблема: в employees есть org_unit_id/job_title, но нет однозначного признака
GrPP/GTP/Luzhniki и офисного/производственного типа. Подразделение не равно площадке,
а должность не даёт надёжного вывода о типе сотрудника.

Предложение:
- `employees.location_tag TEXT NULL` с согласованными значениями GrPP/GTP/Luzhniki;
- `employees.employee_type TEXT NULL` с CHECK office/production;
- `employees.communication_style TEXT NULL` с CHECK informal/formal — предпочтение из анкеты Excel;
- условия аудитории хранить в ограниченном definition шаблона, а при назначении
  сохранять выбранный текст/вопросы в plan_events.definition.

about_me и photo_ref можно хранить в event_answers, без копирования во множество
колонок профиля. Если команда уже имеет авторитетное отображение org_unit→площадка,
отдельный location_tag можно заменить этим отображением после явного согласования.

### 3. Рабочие дни и конец испытательного срока

Проблема: event_time вычисляет только start_date + months + calendar days.
12 событий Excel привязаны к рабочим дням; 2 — к последнему дню испытательного срока.
Нельзя превращать «третий рабочий день» в постоянный offset_days=2.

Предложение:
- `employees.probation_end_date DATE NULL`; снимок `employee_plans.probation_end_date DATE NULL`;
- `employee_plans.work_calendar JSONB` ограниченной структуры: weekdays, holidays,
  extra_workdays. Это снимок графика, не универсальное хранилище кадровых данных;
- для template_events и plan_events: `schedule_anchor TEXT DEFAULT 'start_date'`
  с CHECK start_date/probation_end_date и `workday_no SMALLINT NULL CHECK >0`;
- если workday_no задан, рассчитывать рабочий номер по календарю; иначе применять
  существующие offset_months/offset_days от выбранного якоря;
- обновить assign_plan, configure_event, reschedule_plan и immutable-снимки.
  Расчёт можно делегировать Python, но БД должна хранить правило и принимать
  согласованный результат через штатную операцию, без обхода триггеров прямым UPDATE.

Отдельный phase можно вывести из правила/срока относительно даты выхода; отдельная
таблица фаз не нужна. Не следует хранить несколько противоречащих друг другу признаков.

### 4. Кнопки, фото и материалы исходящих сообщений

Проблема: messages.body хранит только текст, claim_outbox возвращает только body/chat.
У нас есть кнопки, question_code, изображения, карты и PDF; incoming-фото тоже должно
иметь устойчивый ID/ссылку. Самих изображений в исходном Excel нет.

Предложение:
- `messages.payload JSONB NOT NULL DEFAULT '{}'`, ограниченный объект с допустимыми
  options, attachments, question_code и ролью prompt/completion. Установить разумный лимит размера;
- расширить queue_message и claim_outbox для передачи этого объекта;
- в answer_survey_question принимать ID вложения как типизированный ответ attachment;
- хранить файлы вне PostgreSQL, в payload — только ссылки/ID. Отдельная таблица
  файлов сейчас не требуется, если управление файлами уже делает общий backend.

### 5. Срок отправки отдельно от окна ответа

Проблема: deadline_at устанавливается как scheduled_at+response_hours и finish_send
не пересчитывает его при принятии API. Если отправили спустя двое суток, от окна
в 72 часа остаются сутки. Напоминание «завтра выходить» может быть принято уже после выхода.

Предложение:
- `plan_events.send_until_at TIMESTAMPTZ`: предел актуальности первоначальной отправки;
- в finish_send при первом принятии интерактивного события устанавливать
  deadline_at=accepted_at+response_hours; напоминания считать от того же старта;
- в prepare_due_events/claim_outbox использовать send_until_at для scheduled/queued,
  а deadline_at — для ожидания ответа;
- для пребординга ограничить актуальность началом даты выхода в локальном поясе;
- отменять устаревшие prompt/reminder, но не отменять нужное подтверждение завершения.

### 6. Сериализация отправки сотруднику и зависшие отправки

По SQL claim_outbox блокирует employees только до COMMIT. После COMMIT worker A
может отправлять сообщение, а worker B снова выбрать того же сотрудника и другое
pending-сообщение: исключения sending/uncertain у этого сотрудника в функции нет.
Проверка архива на непересечение message_id сама по себе это свойство не проверяет.

Предложение:
- claim_outbox не выбирает сотрудника с незавершённой sending или uncertain отправкой;
- за один захват выдаёт не больше одного сообщения сотрудника;
- generation и двухминутный lease сохранить; uncertain разрешать только после сверки;
- prompt с purpose='notice' тоже должен проверять актуальность связанного вопроса:
  сейчас проверка claim_outbox относится лишь к event/reminder. Например, запрос
  комментария не должен приходить после того, как комментарий уже сохранён.

До согласования: одна очередь delivery с одним worker/concurrency=1. Адаптер дополнительно
останавливает всю отправку при наличии sending/uncertain, чтобы не обойти неизвестный
исход предыдущей попытки. Это временно задерживает и других сотрудников до разрешения
такой записи. Это ограничение эксплуатации, а не исправление общей SQL-функции. В планировщике сроков
можно иметь несколько worker: там уже используются row locks/SKIP LOCKED.

## Что не требуется менять

- BIGINT ID сотрудников: адаптируется кодом и внешним ID.
- Разделение messages/outbox и глобальный max_inbox: используем как есть.
- Версии шаблонов и один active-план: используем как есть.
- accepted отдельно от delivered, generation, uncertain: используем как есть.
- Не нужны ещё одна БД, параллельные onboarding_* таблицы, таблица каждого статуса
  или партиции для небольших планов/событий.
- Нет причин менять RAG/документы/HR-cases ради подключения нашего scheduler.

## Порядок согласования

1. Передать автору БД пункты 1–6; подтвердить типы, названия и обновляемые операции.
2. Получить новую версию архива/миграцию, включая функции и ограничения, а не только колонки.
3. Перевести наш каталог на plan_templates/versions/events и новый survey-контракт.
4. Только после этого включать полный Excel-план через shared-режим.
5. Для текущих простых событий адаптер можно подключать отдельно без расширения БД.

Данные из старой БД не переносились. Если они появятся, перенос требует явной
карты employee/external IDs, версий, event IDs и inbox namespace.
