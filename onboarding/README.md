# Onboarding Engine: основной набор

Это часть общего backend «Корсика»: сценарий адаптации, расчёт дат, проверка
ответов и запуск фоновой обработки. Здесь нет отдельного HTTP-сервера, второй
схемы БД, деморежимов или тестовых файлов.

**Текущая граница:** общая схема `korsik` из архива поддерживает простые
info/task/rating/feedback. Полный Excel с несколькими вопросами, вариантами,
кнопками, материалами и рабочими календарями требует согласованных расширений
из [DB_COMPATIBILITY.md](DB_COMPATIBILITY.md). Чистые календарь и валидатор уже
поддерживают эти требования; это не означает, что их ответы уже можно записать
в текущую общую БД. Автоматически SQL-схема не изменяется.

## Структура

## За что отвечает каждый файл

### `__init__.py` — Python-пакет

Позволяет использовать импорты `onboarding.survey`, `onboarding.scheduler` и т.д.
При импорте не запускает worker, scheduler, сетевые вызовы или подключение к БД.

### `data/korsik_scenario.json` — фиксированный бизнес-сценарий

Один раз подготовлен из Excel: 26 событий, две цепочки до выхода и 24 после.
Конкретному сотруднику подходит часть событий, отфильтрованная по площадке и
типу работы. Внутри — тексты, вопросы, варианты, правила комментариев,
относительные сроки, ключи вложений, ссылка на исходные строки и принятые решения.

Это конфигурация, а не кадровая база. Файл не содержит реальных ответов сотрудников.
Excel повторно не читается. Изменение каталога не переписывает уже назначенные планы:
после согласования с БД оно должно создавать новую версию шаблона.

Срок спорного опроса закреплён по ответу пользователя: +1 календарный месяц +3 недели.
При отсутствии времени принято 10:00 локального времени; окно ответа 3 суток —
проектное допущение, требующее подтверждения HR. Обозначения изображений и PDF
не являются реальными загруженными материалами.

### `scenario.py` — загрузка и проверка каталога

`load_catalog()` читает подготовленный JSON, проверяет версию формата, уникальность
кодов событий/вопросов, фазы и варианты ответов. Ошибка структуры выявляется до
назначения сотруднику. Файл читается при подготовке шаблона, не на каждом tick.
В runtime будущие задания берутся из PostgreSQL.

### `calendar.py` — вычисление персональных дат

`WorkCalendar` содержит рабочие дни недели, исключения и дополнительные рабочие даты.
Корпоративный/сменный график передаёт backend, он не угадывается по должности.
`event_dates()` переводит одно относительное правило в due_at и срок актуальности.
`materialize()` выбирает подходящие события, применяет вариант площадки и сортирует даты.

Поддерживаются календарные дни, рабочие номера дней, календарные месяцы и якорь
конца испытательного срока. Дата выхода — первый рабочий день; две недели после
выхода — +14 календарных дней. Календарный месяц не заменяется 30 сутками.
Результат хранится в UTC, исходный часовой пояс — отдельно. Пребординг перестаёт
быть актуальным в начале даты выхода по местному времени.

Этот файл формирует проект расписания в памяти. Он не обходит assign_plan и
триггеры общей БД прямыми UPDATE: сохранение расширенных правил ожидает доработки БД.

### `survey.py` — проверка одного ответа

`validate_answer(question, raw_value, ...)` поддерживает yes_no, rating, choice,
multi_choice, text и attachment. Ответ принадлежит конкретному question_code.
Фото принимается по attachment_ref, не по тексту «я отправил фото».
`validate_comment()` используется только для явно связанного комментария.

Результат `AnswerResult`:

| Поле | Назначение |
|---|---|
| status | accepted / invalid_answer / pending_confirmation |
| question_code, answer_type | Какому вопросу и формату относится результат |
| value | Нормализованное значение: bool, int, строка или список ID |
| label | Подпись выбранного варианта для HR-анализа; choice не превращается в рейтинг |
| comment_required | Требуется ли пояснение по настройке этого вопроса |
| reason_code, reply_text | Код ситуации и подготовленная подсказка при неверном вводе |
| profile_update | Предлагаемое изменение профиля, например formal/informal; не выполняется само |

`invalid_answer` — обычный результат. Значение не записывается как ответ, вопрос
не завершается; Router сохраняет входящее сообщение, ставит подсказку в общий
outbox и завершает inbox как обработанный. Повторять его как техническую ошибку нельзя.
Для multi_choice окончательное принятие требует `confirmed=True`; промежуточный
набор не завершает вопрос и не запускает анализ как окончательный ответ.

Пример:

```python
from onboarding.survey import validate_answer

question = {"code": "access", "type": "yes_no", "text": "Все доступы получены?", "comment_on": [False]}
result = validate_answer(question, "не знаю")
print(result.status)      # invalid_answer
print(result.reply_text)  # Подсказка выбрать да/нет
```

Валидатор не пишет в БД и не отправляет сообщения. Сохранение ответа, изменение
текущего вопроса, outbox и завершение inbox должны быть атомарной операцией общего
backend. Эта операция для новых типов ждёт расширения общей БД. При простой
оценке текущая answer_event сама создаёт запрос комментария; не создавать второй
дубликат на основании comment_required.

`QuestionConfigurationError` означает ошибку настройки, а не ошибку сотрудника.
Нельзя превращать её в бесконечную просьбу «ответьте правильно».

### `shared_db.py` — единственная точка SQL

Работает с таблицами `korsik.*`, не объявляет новые ORM-модели и не выполняет DDL.
Все пользовательские значения передаются параметрами SQL.

- `check_database()` проверяет PostgreSQL 17+ и наличие функций из архива.
- `resolve_employee_id()` находит BIGINT-ID по external_employee_id. Строковый ID
  нельзя слепо привести к int и считать общим ключом.
- `assign_plan()` вызывает штатную assign_plan с HR, сотрудником и опубликованной версией.
- `answer_simple_event()` вызывает answer_event для rating/comment/task_confirm/feedback.
  Входящий webhook и дедупликацию по provider_event_id обрабатывает общий max_inbox-worker.
- `get_progress()` читает последний/активный план и его события.
- `recover_leases()` и `prepare_due_events()` вызывают операции общей БД.
- `claim_message()`, `delivery_is_current()`, `finish_send()` обслуживают аренду отправки.
- `unresolved_delivery()` выявляет незавершённую/неопределённую отправку.

Сессию и commit/rollback предоставляет вызывающий backend. У функций нет скрытого
собственного соединения. Два прежних импорта run_* сохранены как тонкие перенаправления
в scheduler.py; второй реализации планировщика нет.

### `scheduler.py` — рабочая фоновая обработка

`run_scheduler_tick(Session)` делает короткую транзакцию: восстанавливает аренды
по правилам общей БД и вызывает подготовку наступивших событий/напоминаний.

`run_delivery_tick(Session, send_to_max)` берёт одно сообщение, фиксирует аренду,
закрывает транзакцию, вызывает сеть, затем отдельно сохраняет результат. Не
держит PostgreSQL-блокировку во время HTTP. Просроченная generation не применяется.

MAX-адаптер получает message_id, generation, employee_id, step_id, chat_id, text,
idempotency_key и purpose. Возвращает непустой внешний ID принятого API сообщения.
Он должен использовать конечный timeout меньше двухминутной аренды.

Результаты:
- подтверждённый успех → accepted; это ещё не подтверждение доставки delivered;
- `RejectedBeforeAcceptance` → сервер точно не принял, БД назначает retry/dead;
- timeout/неизвестная ошибка → uncertain, поскольку сообщение могло дойти;
- потерянная generation → stale, не выдаётся за успех.

Повторами и задержкой управляют функции общей БД. Нет sleep на каждого сотрудника
и отдельного таймера на каждый этап. Стабильный idempotency_key передаётся транспорту;
однократная доставка зависит также от возможностей API MAX.

До исправления claim_outbox из отчёта: только один delivery-worker. Если есть
sending/uncertain, адаптер консервативно останавливает общую отправку до разрешения
ситуации. Это может задержать других сотрудников, а не «исправляет» схему незаметно.

### `tasks.py` — связь с Celery Beat и worker

`register_tasks(celery_app, Session, send_to_max)` добавляет две задачи в уже
существующее Celery-приложение команды. Другие периодические задачи не удаляются.

- onboarding.schedule: каждые 30 секунд запускает run_scheduler_tick;
- onboarding.deliver: каждые 5 секунд запускает run_delivery_tick в очереди onboarding.delivery.

Beat — будильник; Redis передаёт короткие команды worker; worker вызывает Python.
Персональные даты и результаты остаются в PostgreSQL. Нужен один Beat. Для
onboarding.delivery пока нужен один worker/concurrency=1; другие worker не должны
забирать эту очередь. Временные интервалы — частота опроса, не обещание доставки
ровно в секунду: задержка зависит от очереди, БД и транспорта.

Аргумент storage="shared" оставлен для совместимости старых вызовов. Иных режимов
нет: legacy удалён. Файл не создаёт второе Celery app и не запускает Redis.

### `requirements.txt` — зависимости механик

SQLAlchemy для сессий/SQL, psycopg для PostgreSQL, Celery с Redis-драйвером для
периодической обработки. Не включает FastAPI, Streamlit, LLM или тестовые библиотеки.
Перед установкой рекомендуется обновить pip в своём venv — старый pip 21.2.4
уже приводил к конфликту разрешения зависимостей в этом проекте.

### `DB_COMPATIBILITY.md` — договорённости с автором БД

Сохраняет сверку с архивом и конкретные шесть групп расширений. Это документ для
согласования, не исполняемая миграция. После изменения БД нужно получить новую
версию схемы/функций и адаптировать сохранение полного сценария.

### Корневой `.env.example` — образец настроек

Показывает имена DATABASE_URL, CELERY_BROKER_URL и timeout MAX-адаптера. Настоящие
значения хранить в окружении или локальном `.env`. Модуль сам `.env` не читает:
настройки загружает общий backend. Никаких реальных паролей в примере нет.

### Корневой `.gitignore` — что не отправлять в Git

Исключает venv, байткод, локальные секреты, логи, состояние Beat, локальные данные
PostgreSQL/Redis, кэши и dist-архивы. `.env.example`, код, сценарий JSON и документы
остаются доступными для коммита. Реальные ответы и дампы БД не кладутся в сценарий.

## Подключение к проекту команды

```bash
python -m pip install --upgrade pip
python -m pip install -r onboarding/requirements.txt
```

Backend создаёт SQLAlchemy engine/Session и Celery app из своих настроек,
предоставляет синхронную send_to_max и регистрирует модуль:

```python
from onboarding.shared_db import check_database
from onboarding.tasks import register_tasks

with Session.begin() as session:
    check_database(session)

register_tasks(celery_app, Session, send_to_max)
```

Session и send_to_max здесь зависимости общего приложения. HR-ID берётся из
проверенной сессии, сотрудник/событие — из проверенного контекста. Общую БД
устанавливает автор/администратор по своему архиву, не этот модуль. Никаких
onboarding_* таблиц создавать не надо.

При подключении Router отличает ответ, комментарий, вопрос к RAG и запрос HR.
Модель не должна угадывать bool из «не знаю». Внутри транзакции перепроверяются
текущий вопрос/версия/срок и принадлежность сотруднику. Ответы HR и расписание
не проходят распознавание намерений как сообщения сотрудника.

## Оставшиеся границы

- Реальная запись новых типов ответов и работа полного Excel ждут расширений общей БД.
- Регистрация/SSO/MAX, реальные медиа и кабинет HR предоставляет команда.
- Перенос/отмена плана должны использовать штатные операции общей БД.
- Вопрос на «вы» требует утверждённых текстов, автоматическое склонение не добавлено.
- Общая PostgreSQL 17+ и живой MAX в этом чате не подключались.
- Демопроцессы beat_demo/manual_demo и старые команды удалены из основного набора.
  Если они ещё работают в открытых терминалах, остановить их Ctrl+C; процессы
  общего приложения запускаются отдельно по конфигурации backend-команды.

## Короткая приёмка без тестовых файлов

Проверить вручную один план, один tick и одну отправку на тестовой PostgreSQL 17+.
Проверить одну оценку 7 с комментарием и одну 9 без него, один невалидный ввод и
один сбой MAX. Это проверка интеграции; большой набор тестов в пакет не включён.
