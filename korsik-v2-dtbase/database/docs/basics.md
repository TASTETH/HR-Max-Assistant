## 8. Объяснение ключевых понятий

**Primary Key.** Решение → `employees.id` идентифицирует одну карточку → иначе нельзя надёжно сослаться на человека → у Алексея есть один id на регистрацию, планы и переписку → identity может иметь пропуски; номер не секрет и не авторизация.

**Foreign Key.** Решение → `plan_events(plan_id,employee_id,version_id)` ссылается на тот же набор у плана → нельзя прикрепить этап к чужому сотруднику или другой версии → кнопка задания Ирины не изменит этап Алексея → нужны совпадающие типы, дополнительные UNIQUE-цели и передача всех частей связи.

**UNIQUE и PK.** Решение → PK у invitations — id, UNIQUE — token_hash → приглашение имеет собственную идентичность и запрещает повтор секрета → поиск идёт по хешу, а в журнале используется id → UNIQUE сам по себе допускает NULL; здесь hash явно NOT NULL. У таблицы один PK и может быть несколько UNIQUE.

**Индекс и ограничение.** Решение → индекс `(employee_id,created_at DESC,id DESC)` ускоряет переписку → не надо читать всю историю → берём следующую страницу по последнему времени/id → индекс расходует место/WAL, но не запрещает дубли текста. PK/UNIQUE создают обеспечивающие индексы, обычный INDEX сам по себе не является правилом целостности.

**Составной ключ.** Решение → PK у answer_sources `(message_id,chunk_id)` → одна и та же цитата не должна повториться в ответе → два разных ответа могут ссылаться на один фрагмент → запросы по одному chunk_id без message_id не используют левую часть этого индекса. Отдельный id потребовал бы ещё один UNIQUE той же пары.

**Партиция.** Решение → пока обычные таблицы → разбиение на месяцы усложнило бы исторические FK и глобальный event_id → один webhook не применится второй раз после смены месяца → при очень больших объёмах пакетное удаление сложнее, поэтому сначала измеряем. Партиция распределяет строки по физическим частям, а индекс ищет строки внутри выбранных частей.

**Ключ партиционирования.** Решение → не объявлять фиктивный UNIQUE(id) у таблицы RANGE(created_at) → PostgreSQL 17 требует все колонки partition key в PK/UNIQUE → PK(id,created_at) потребовал бы те же части у FK на сообщения → сложнее API, а UNIQUE(event_id,created_at) всё равно допускает повтор event_id с новым временем. Это одна из причин сохранить inbox обычным.

**Scheduler.** Решение → worker блокирует карточки с наступившей работой через SKIP LOCKED и в короткой транзакции создаёт messages/outbox и меняет событие → второй worker пропускает захваченную работу → приветствие не создаётся дважды → очередь не гарантирует порядок сетевой доставки при нескольких sender; критическая последовательность задаётся зависимостями.

**Ответ HR.** Решение → исходящее messages.author='hr' и FK на case/HR → текст нельзя переписать LLM и записать как нейросетевой → sender отправляет неизменённый body из outbox → сеть может дать неопределённый результат; API acceptance и receipt сохраняются раздельно.

**Граница ответственности.** Решение → БД проверяет PK/FK/UNIQUE/CHECK, некоторые переходы, immutable историю и транзакционные блокировки; backend проверяет SSO/владение, webhook, подпись callback, смысл маршрута и внешние API → вопрос про отпуск во время опроса уходит в RAG без изменения rating → семантику текста и реальные права пользователя нельзя доказать одним employee.hr_id.


Решение → PK(event_id,question_code) у event_answers → несколько вопросов одного survey не затираются → оценка и фото имеют разные коды → FK на определение вопроса внутри JSON реализуется trigger, не обычным CHECK.

Решение → outbox.employee_id + partial UNIQUE sending/uncertain → блокировка доставки переживает COMMIT → следующий sender ждёт исхода первой попытки → требуется сверка uncertain; row lock сам по себе не живёт между HTTP-вызовами.
