# HR-Max-Assistant — Корсик

Проект команды **NLP**, хакатон 2026.

Участники: Дзарасов Руслан Аланович, Пимкин Максим Сергеевич, Николаев Роман Петрович, Кравченко Федор Максимович, Струбалин Никита Павлович.

Реализованы приём `message_created`, `message_callback`, `bot_started`, проверка `X-Max-Bot-Api-Secret`, устойчивый inbox, Router, опросы, HR-анализ через Ollama, RAG с источниками и outbox/Sender. В Git находятся исходники и `.env.example`; токены, реальные ответы сотрудников, импортированные материалы, базы данных и логи хранятся локально.

## Структура и границы MVP

| Каталог | Назначение |
|---|---|
| `app/main.py`, `app/max/` | HTTP webhook и клиент MAX |
| `app/router/` | Правила, контекст, обработчики, устойчивые задания и отдельный интерфейс Router |
| `app/hr/` | Анализ обратной связи через Ollama и правила эскалации |
| `app/rag.py` | Поиск выдержек по разрешённым корпоративным источникам |
| `app/tasks.py` | Celery/Beat и локальный runner |
| `database/` | SQL, который устанавливает приложение |
| `onboarding/` | Сохранённый модуль полного сценария, календаря и интеграции с общей БД |
| `tests/` | Проверки адаптера, бизнес-сценариев, PostgreSQL, конфигурации и туннеля |

Каталог `onboarding/data/korsik_scenario.json` содержит подготовленный полный сценарий. Его механики и ограничения описаны в [onboarding/README.md](onboarding/README.md), согласование с общей БД — в [onboarding/DB_COMPATIBILITY.md](onboarding/DB_COMPATIBILITY.md). Runtime бота сейчас использует демонстрационный план из `app.cli.seed`: публикация файлов полного сценария не означает его автоматическое назначение сотрудникам. Для SQLAlchemy-сессий используйте `SQLALCHEMY_DATABASE_URL`; runtime на psycopg использует `DATABASE_URL`.

Архив `korsik_postgresql17_v2.zip` сохранён из существующего репозитория как отдельная поставка БД. Он не устанавливается автоматически поверх работающей схемы. [docs/router_logic.md](docs/router_logic.md) — спецификация проектирования; фактическая граница реализации описана в этом README.

## Первый запуск после git clone

```powershell
git clone https://github.com/TASTETH/HR-Max-Assistant.git
cd HR-Max-Assistant
python -m app.configure
```

Команда создаёт `.env` со случайными паролями и секретом webhook. Существующий `.env` сохраняется. В созданном файле заполните `MAX_BOT_TOKEN`, проверьте `MAX_BOT_URL`; остальные адреса настраиваются для вашего окружения. Необязательные контакты HR и постоянный домен можно заполнить позднее. Дополнительная команда для Windows: `./setup-env.ps1`.

Для запуска без Python на хосте можно скопировать `.env.example` в `.env` и вручную заменить все `replace_with_random_*`, согласовав пароли с URL подключения, затем запустить Docker Compose.

## Локальный запуск на Windows

Python 3.12 и PostgreSQL 17+ должны быть установлены. Приложение создаёт собственный кластер в `data/postgres`, доступный только по `127.0.0.1:55432`. Имеющаяся служба PostgreSQL на порту 5432 остаётся отдельной. Если бинарные файлы PostgreSQL не найдены автоматически, задайте `POSTGRES_BIN` с путём к каталогу `bin`.

В PowerShell из папки проекта:

```powershell
.\start-bot.ps1
```

Скрипт устанавливает зависимости в `.venv`, запускает FastAPI и фоновые обработчики на `127.0.0.1:8000`, открывает временный HTTPS-туннель, проверяет публичный `/health/ready`, записывает публичный URL в `.env` и регистрирует webhook в MAX. По умолчанию пробуется Cloudflare; если сеть не позволяет соединиться, используется SSH-туннель [localhost.run](https://localhost.run/docs/). API и туннель работают фоновыми процессами. Логи и PID находятся в `data/`; данные сохраняются между запусками. Компьютер должен оставаться включённым.

Если сеть не позволяет подключиться к Cloudflare, выберите `localhost.run` явно: `.\start-bot.ps1 -Provider localhost-run`. Для собственного домена заранее настройте постоянный HTTPS-вход.

Бесплатный `localhost.run` периодически меняет имя даже внутри одного соединения. Скрипт запускает `app.tunnel_watch`: тот выбирает актуальное имя из лога, проверяет доступность API, обновляет `.env` и подписку MAX, затем удаляет только прежнюю подписку этого экземпляра. Другие подписки не удаляются. Это режим демонстрации; постоянный домен предпочтителен для эксплуатации.

Для одного локального сервера без публичного туннеля:

```powershell
.\start-local.ps1
```

Остановка API и туннеля:

```powershell
.\stop-local.ps1
```

База данных при этом продолжает работать; данные не удаляются. Для остановки собственного PostgreSQL используйте `pg_ctl -D <папка проекта>/data/postgres stop -m fast` из каталога его `bin`.

## Домен polyplastic.cc.cd

`localhost` доступен самому компьютеру. MAX нужен публичный HTTPS-адрес на порту 443 с доверенным сертификатом: [требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions).

Для постоянного домена настройте Cloudflare Tunnel с опубликованным hostname `polyplastic.cc.cd` и origin `http://127.0.0.1:8000`. Домен должен находиться в вашей зоне Cloudflare: [официальная инструкция](https://developers.cloudflare.com/tunnel/get-started/). После настройки:

```powershell
.\start-bot.ps1 -PublicUrl https://polyplastic.cc.cd
```

Команда с `-PublicUrl` использует уже работающий публичный вход, останавливает автоматическое переключение на меняющиеся адреса localhost.run и не создаёт временный туннель. Один CNAME на случайный `trycloudflare.com` не заменяет настройку постоянного туннеля и TLS для своего домена.

Временный туннель подходит для демонстрации, требует сетевой доступ к Cloudflare и меняет адрес при новом запуске. Постоянное развёртывание требует named tunnel или собственного HTTPS reverse proxy. Пока публичный `/health/ready` недоступен, скрипт не меняет подписку MAX. Если туннель блокируется сетью, локальный API остаётся доступен, а в логах есть причина.

## Подключение сотрудников

Бот принимает HR-данные только для сотрудника с персональным приглашением. При обычном `/start` новый аккаунт получает приветствие и пояснение о приглашении. Это сохраняет привязку сотрудника к HR и площадке.

```powershell
.\.venv\Scripts\python.exe -m app.cli invite --site GrPP
```

Команда вернёт одноразовую ссылку `https://max.ru/id5021013384_2_bot?start=...` и `employee_id`. Сотрудник открывает ссылку, вводит ФИО и телефон, подтверждает анкету. Администратор проверяет её и назначает демонстрационный план:

```powershell
.\.venv\Scripts\python.exe -m app.cli approve 1 --site GrPP --job-title 'Специалист' --start-date 2026-10-24
```

Замените ID, площадку, должность и дату реальными значениями. Доступны `GrPP`, `GTP`, `Luzhniki`. Демонстрационный план содержит приветствие, оценку 1–10 и вопрос о продолжении работы. Он показывает сквозной MVP, а полный календарь Excel требует отдельного заполнения шаблонов; спорные даты спецификации автоматически не подставляются.

Команды в MAX: `/help`, `/HR`, `/Food`, `/plan`, `/resume`. Оценка ниже 8 запрашивает комментарий. `/Food` сохраняет ожидающий вопрос. Ответ о намерении уйти сразу ставится в HR-анализ; подтверждённый сигнал создаёт обращение высокого приоритета. Отрицание намерения не служит самостоятельным основанием для такого обращения. Старые и чужие кнопки отклоняются.

Укажите проверенные `HR_MAX_CHAT_ID` и `HR_CONTACT_URL` в `.env`, затем выполните `python -m app.cli seed` и перезапустите сервер. Уведомления направляются только HR, назначенному сотруднику. Без настроенного chat ID обращения сохраняются в БД; отправка уведомления человеку не заявляется выполненной. Ответ HR без пересказа модели:

```powershell
.\.venv\Scripts\python.exe -m app.cli hr-reply 1 --hr-id 1 --text-file .\reply.txt
```

Управляющие команды CLI предназначены для доверенного оператора с административным DSN; HTTP-методы управления HR наружу не открыты.

## База знаний и питание

По умолчанию RAG использует русский полнотекстовый поиск PostgreSQL и возвращает точные выдержки с названием и расположением источника. Он не генерирует новые кадровые правила. При отсутствии совпадения вопрос передаётся HR. `RAG_URL` позволяет подключить внутренний LLM/RAG-сервис по контракту `RagRequest → RagAnswer`; права на источники повторно проверяет БД перед сохранением и отправкой.

Импорт отдельного UTF-8 текста:

```powershell
.\.venv\Scripts\python.exe -m app.cli import-document .\policy.txt --title 'Регламент' --code policy
```

По умолчанию документ доступен всем активированным сотрудникам. `--org-unit-id` ограничивает его подразделением. Импорт предоставленного сборника:

```powershell
.\.venv\Scripts\python.exe -m app.cli import-materials '.\materials\ПОЛИПЛАСТИК_полный_текст_всех_материалов.txt'
```

Сам сборник предоставляется отдельно; каталог `materials/` исключён из Git. Из сборника выбираются четыре корпоративных документа. Кейс хакатона, техническое задание и конспект не индексируются как корпоративные правила. Тексты используются как данные, инструкции из них не исполняются. Распознанные материалы помечаются в названиях источников.

Утверждённый текст питания каждой площадки хранится в `korsik_router.materials` с `code='food'`, `site_code='GrPP'|'GTP'|'Luzhniki'`. В предоставленном текстовом сценарии карты питания отмечены как отдельные приложения, содержимого этих приложений нет. Бот сообщает об отсутствии материала; условия питания не выдумываются. Изображения поддерживают HTTPS URL или MAX upload token, документы — MAX upload token.

## Redis + Celery + Docker

Для серверного запуска включён полный стек:

```powershell
docker compose up --build -d
docker compose exec api python -m app.cli check-bot
docker compose exec api python -m app.cli subscribe
```

`init` создаёт схему и минимальные справочники, `api` принимает webhook, `worker` выполняет обработку, `beat` повторно сканирует устойчивые очереди и запускает расписание. PostgreSQL и Redis не публикуют порты наружу. API привязан к `127.0.0.1:8000`, перед ним нужен HTTPS вход.

В нативном режиме Windows используются те же обработчики и таблицы, а задания подбирает локальный фоновый runner без Redis. Не запускайте его одновременно с Celery для одной демонстрационной конфигурации. Для ручного Celery на Windows используйте `--pool=solo`; Docker запускает Linux worker.

Ollama подключается через `OLLAMA_BASE_URL`; модель задаётся `OLLAMA_MODEL`. Опросы, явный запрос HR и поиск выдержек работают независимо от доступности модели. Ошибки анализа имеют отдельные статусы и повторяются; ошибка модели не подменяется отрицательным результатом анализа.

## Надёжность и диагностика

Webhook фиксирует нормализованное событие до `200 OK`; уникальность обеспечивается MAX message ID / callback ID. `bot_started` имеет стабильный составной ключ. Redis лишь ускоряет подбор: его сбой не теряет inbox. Внешние вызовы MAX и моделей выполняются после завершения транзакции.

Outbox использует lease и generation. MAX не документирует ключ идемпотентности для `POST /messages`, поэтому после таймаута записи, HTTP 5xx или неоднозначного сбоя отправка получает `uncertain` и не повторяется автоматически. Оператор сверяет её с MAX; известные отказы до приёма допускают повтор. У каждой части длинного сообщения сохраняется отдельный MAX ID, принятые части повторно не отправляются. Ограничение скорости применяется в PostgreSQL ко всем sender.

`accepted` означает приём MAX API, а не прочтение сотрудником. Событие подтверждения доставки не выдумывается: три подключённых типа обновлений его не дают. Соответствующие статусы HR-case автоматически не закрываются как доставленные.

```powershell
.\.venv\Scripts\python.exe -m app.cli status
.\.venv\Scripts\python.exe -m app.cli subscriptions
.\.venv\Scripts\python.exe -m app.cli check-bot
```

`GET /health/live` проверяет процесс; `GET /health/ready` проверяет доступность БД и транспортных таблиц. Секреты и произвольные тела ответов MAX в диагностике не выводятся. Сертификат для нового MAX API включён в `certs/`; проверка TLS остаётся включённой.

Проверки:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:RUN_POSTGRES_TESTS='1'
.\.venv\Scripts\python.exe -m pytest -q
```

Интеграционные проверки создают отдельную БД `korsik_test_*` и удаляют только её. Проверяются приём webhook, повторы, регистрация, опрос и прерывания, источники RAG, передача HR, долгие сообщения и неопределённая доставка. MAX подменяется тестовым клиентом, сотрудникам тестовые сообщения не рассылаются.

Основа SQL взята из предоставленного ранее `korsik_postgresql17.zip` (SHA-256 `6268977C0A58506A6F6F9210F357D75DDFB255A8BCEA7753DBEA80F58A2DCF32`). В `operations.sql` добавлена сериализация отправок одного сотрудника; расширения канала вынесены в `002_transport.sql`. Существующее ядро Router остаётся отдельным модулем.

## Отправка изменений в Git

Обычный цикл работы с существующим репозиторием:

```powershell
git add .
python scripts/check_git_content.py
git diff --cached --stat
git commit -m "Add MAX webhook, HR Router, RAG and deployment"
git pull --rebase origin main
git push -u origin main
```

Проверка анализирует подготовленный Git snapshot и содержимое ZIP: локальные runtime-файлы, известные секреты из `.env`, приватные ключи и токены не должны попасть в коммит. Значения секретов при проверке не печатаются. Корпоративные документы и ответы сотрудников остаются вне репозитория; подготовленный сценарий `onboarding/data/*.json` версионируется.

GitHub Actions запускает проверки на Python 3.12 и отдельной PostgreSQL 17. Живой MAX, VPN и реальные секреты для CI не нужны. Для быстрой локальной проверки без PostgreSQL выполните `python -m pytest -q` без `RUN_POSTGRES_TESTS=1`.
